## 摘要
本文提出了LeakyLMs，一组从生产语言模型中泄漏专有模型、架构和部署信息的攻击。LeakyLMs首次证明，仅通过令牌生成时序即可推断出关键的模型和部署细节，即使是通过远程API进行交互。LeakyLMs引入了两种核心攻击。第一种攻击针对推理优化和部署策略。例如，我们的攻击检测提供者是否使用推测解码（一种广泛部署的推理时优化），并进一步识别管道中使用的草稿模型的上下文长度。我们的测量表明，Google Gemini Flash 2.5使用了推测解码，草稿上下文窗口约为128K令牌。第二种攻击恢复了关键的架构属性，包括Transformer层数、隐藏维度大小和注意力头数。为了实现这一点，LeakyLMs建立了现代NVIDIA GPU上令牌生成时序的详细准确模型，描述了延迟如何随模型配置和硬件参数变化。然后，攻击使用此时序模型在架构空间中进行搜索。在Llama模型的实验中，近正确的架构配置在90%以上的情况下出现在前10个猜测中。

## Abstract
This work presents LeakyLMs, a set of attacks that leak proprietary model, architecture, and deployment information from production language models. LeakyLMs is the first to demonstrate that key model and deployment details can be inferred using only token generation timing, even when interacting through remote APIs. LeakyLMs introduces two core attacks. The first attack targets inference optimizations and deployment strategies. For example, our attack detects whether a provider uses speculative decoding, a widely deployed inference-time optimization, and further identifies the context length of the draft model used in the pipeline. Our measurements show that Google Gemini Flash 2.5 uses speculative decoding with a draft context window of approximately 128K tokens. The second attack recovers key architectural properties, including the number of transformer layers, hidden dimension size, and number of attention heads. To achieve this, LeakyLMs builds a detailed and accurate model of token-generation timing on modern NVIDIA GPUs, characterizing how latency scales with model configuration and hardware parameters. The attack then performs a search over the architecture space using this timing model. In experiments with Llama models, the near-correct architectural configuration appears in the top-10 guesses more than 90% of the time.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **研究动机**：当前AI领域竞争激烈，头部企业的模型架构、部署策略（如推理优化）被视为核心商业机密，通常不予公开。然而，这些生产级LLM在提供流式生成时，会暴露每个令牌的生成时序（per-token timing），且用户可通过API或Web界面精确测量这些时序。
- **核心问题**：能否仅通过逐令牌的生成时序，从未知远程API中反向推断出模型的架构参数（层数、隐藏维度、注意力头数）和部署细节（是否使用推测解码、草稿模型上下文长度）？
- **整体含义**：这是首次系统论证了时序侧信道可以泄露LLM内部结构和部署优化信息，对AI产业的知识产权保护和安全性构成重要威胁。

## 2. 论文提出的方法论

### 核心思想
- 利用逐令牌时序的差异性：生成不同令牌的延迟与模型架构参数（H, L, A, I）和部署优化（如推测解码）存在函数关系。通过精心构造输入，诱发可测量的时序变化，从而反推未知信息。
- 两种攻击：
  - **攻击一（推测解码检测与参数估计）**：利用草稿模型通常上下文窗口小于主模型的特点，故意拉长提示词超过草稿模型能力，导致草稿-主模型频繁冲突，产生时序尖峰，从而检测推测解码并估算草稿上下文长度。
  - **攻击二（架构参数恢复）**：构建一个基于线性回归的GPU上LLM令牌生成时序预测器，将架构参数映射到逐令牌延迟；然后对于未知模型，测量其时序，在架构空间中搜索最匹配的候选。

### 关键技术细节
1. **推测解码攻击**：
   - 构造“记住一个长数字”的提示，通过填充不同长度使提示词长度变化，但语义复杂度基本一致。
   - 测量不同提示长度下的逐令牌延迟，观察是否存在一个断点（breakpoint），超过该长度后延迟显著增大。
   - 断点位置对应草稿模型的最大上下文长度（减去提示中起始部分）。
2. **架构参数攻击**：
   - **离线阶段**：对公开模型（如Llama 3.2 1B）进行剖析，分解Transformer各子组件（注意力、MLP、归一化等），推导每个操作的理论计算/内存复杂度（例如注意力中的 O(TH²L) 等），以此作为特征项。然后收集不同架构配置（改变H、L等）下的实际测量时序，使用线性回归拟合系数，得到可解释的预测模型。
   - **非线性校正**：针对cuBLAS动态选择不同核函数导致的非线性，训练一个LightGBM分类器预测所选核，再用随机森林估计该核的运行时，对线性预测结果进行校正。
   - **适配FlashAttention和KV-cache**：调整扩展项以反映FlashAttention的I/O复杂度，以及PreFill/Decode两阶段的不同缩放关系。
   - **在线阶段**：对目标模型，使用同一组提示词测量时序，枚举候选架构配置（搜索空间经过合理剪枝），用预测器生成预期时序，计算与实测时序的RMSE，排序候选，取前几名作为推断结果。

### 公式与算法流程（文字说明）
- 对单个子组件（如注意力），运行时近似为：time ≈ a₁·(TH²L) + a₂·(T²HL) + ... + C，系数通过线性回归学习。
- 整体模型时序 = 各子组件时序之和 + 开销项。
- 搜索过程：对于每个候选 (H, L, A, I)，预测一个时序向量（对应不同T），与实测向量比较RMSE，排序输出。

## 6. 论文的主要结论与发现

1. **推测解码可被时序检测**：成功检测到Google Gemini Flash 1.5/2.5/2.5 Lite使用推测解码，并估计草稿模型上下文长度分别为32K、128K、128K。其他模型（OpenAI GPT-4o、Cohere等）未检测到时序尖峰。
2. **架构参数可被时序恢复**：
   - Eager Attention实现下，NRMSE可低至0.119（测试集）；Top-5准确率在只推断单参数时超过70%，同时推断H和L时约65%。
   - FlashAttention2和KV-cache模型的预测精度稍低（NRMSE约0.18-0.25），但Top-5准确率仍可观（L约84-97%、H约71-100%）。
   - 跨模型族泛化良好，在Qwen、Phi、Gemma模型上Top-5准确率仍达47-100%。
   - 真实远程API（W&B Llama 3.1 8B）实验中，正确H被排首位，正确L排第4，成功恢复。
3. **线性回归模型+校正**相比纯理论模型能显著提升预测准确率。
4. 这些结果警示：提供流式输出的LLM API面临严重的时序侧信道风险。

## 7. 优点

1. **首次系统性证明时序侧信道泄露LLM架构和优化信息**：之前研究多聚焦于重量级测量（logits、缓存）或特定模型指纹，本文更为全面。
2. **可解释性强**：采用线性回归模型，各项系数对应理论计算复杂度，可以清晰解释各因素对时延的影响。
3. **泛化性好**：在多种GPU架构、多种实现（Eager/FlashAttention）、多种模型族上验证，且校正方法有效。
4. **实用性强**：仅需标准API访问，无需特权；攻击成本低（少量请求和CPU时间）。
5. **负责任披露**：向Google报告了推测解码漏洞。
6. **方法模块化**：可方便扩展以建模新的推理优化或GPU架构。

## 8. 不足与局限

1. **假设已知GPU类型**：对于完全黑盒场景（未知GPU），攻击可能失效，因为时序模型依赖具体硬件参数。
2. **假设单GPU推理**：未考虑多GPU并行或流水线并行导致的时序抖动，实际大规模部署可能更复杂。
3. **推测解码攻击可能漏报**：如果草稿模型上下文与主模型相同，则不会出现时序尖峰，可能产生假阴性。
4. **网络噪声**：远程API实验虽验证了可行性，但网络RTT标准差较小（<5%），如果RTT波动更大，可能掩盖信号。
5. **搜索空间需人工定义**：架构参数搜索依赖先验知识（如H为64的倍数），对于全新设计可能无效。
6. **跨模型族泛化实验数据量有限**：每个额外模型族仅用了约40个配置，且未包含极大或极小参数模型。
7. **未评估对FP8/int4量化等更复杂优化的时序影响**：本文假设FP16精度，实际部署可能使用量化，时序特性可能变化。
8. **防御讨论尚浅**：仅提出恒定时间或缓冲策略，未提供实际可部署的防护方案。
