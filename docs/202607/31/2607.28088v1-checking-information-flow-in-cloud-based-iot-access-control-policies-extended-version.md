## 摘要
许多物联网技术的云提供商提供访问控制机制，其正确配置对安全性至关重要。然而，在设备具有不同信任级别或分属于不同子系统的环境中，单独验证权限是不够的。这项工作分析了物联网访问控制策略，以识别设备之间非预期信息流带来的潜在安全漏洞。为此，我们正式对AWS IoT Core的组件进行建模，并定义一个信息流图来捕获访问控制策略所允许的设备之间的通信。我们利用SMT求解器构建该图的有限表示，从而能够验证设备之间的信息流。我们在一个名为IOT:POKER的工具中实现了我们的方法，并在一个现实场景和多个实际策略上进行了评估。

## Abstract
Many cloud providers for IoT technologies offer access control mechanisms whose proper configuration is critical for security. However, verifying permissions in isolation is insufficient in a setting where devices have different levels of trust or are compartmentalised in various subsystems. This work analyses IoT access control policies to identify potential security vulnerabilities from unwanted information flow between devices. To this end, we formally model AWS IoT Core's components and define an information flow graph to capture the communication among devices permitted by the access control policies. We build a finite representation of the graph by leveraging an SMT solver, thus enabling the verification of information flow between devices. We implement our approach in a tool called IOT:POKER, and assess it on a realistic scenario and several real-world policies.

### 1. 核心问题与整体含义（研究动机与背景）

- **研究背景与问题**：物联网（IoT）云平台（如 AWS IoT Core、Azure IoT Hub）提供了访问控制机制，开发人员通过编写 IoT 策略来规定设备可以执行的操作（连接、发布、订阅、接收）与访问的资源（主题、主题过滤器、客户端 ID）。然而，现有研究大多只关注**单条策略**的权限配置是否正确（如检测越权、权限过度宽松），而忽略了在多设备、多子系统环境下，策略之间相互组合可能产生的**跨设备信息流**安全风险。
- **核心安全威胁**：在真实 IoT 部署中，设备具有不同的信任级别和敏感性（如门锁、烟雾探测器 vs. 灯泡、传感器）。若某些设备被攻陷（或策略配置错误），攻击者可以利用设备间的通信路径，间接影响关键设备（破坏完整性）或窃取敏感信息（破坏机密性）。
- **关键漏洞示例**：论文揭示了 **"通配符注入攻击"（wildcard injection attack）**——攻击者在连接时使用包含 `#` 或 `+` 等 MQTT 通配符的客户端 ID，这些字符在客户端 ID 中是普通字符，但经过 `$clientId` 变量替换后注入策略，在主题过滤器中变为通配符，从而绕过原本的限制，订阅本不应可访问的主题。
- **论文目标**：形式化建模 AWS IoT Core 的核心组件，构建信息流图以捕捉策略允许的所有设备通信，并利用 SMT 求解器实现可扩展的信息流验证——即检查设备间是否存在允许的、可能破坏机密性或完整性的信息流路径。

### 2. 方法论：核心思想、关键技术细节与流程

- **形式化模型（底层语义）**
  - **资源（Resource）**：客户端 ID、主题（topic）、主题过滤器（topic filter）。主题过滤器中的 `+`（单层通配符）和 `#`（多层通配符）遵循 MQTT 匹配语义。
  - **资源表达式（Resource Expression）**：策略中使用的字符串，可包含 AWS 通配符 `?`（匹配任意单个字符）和 `*`（匹配任意字符序列），以及变量 `$clientId`（在策略实例化时替换为设备实际的客户端 ID）。
  - **策略（Policy）**：一组语句 `(ε, α, R)`，其中 ε ∈ {Allow, Deny}，α ∈ {Con, Pub, Rec, Sub}，R 为一组资源表达式。采用 **默认拒绝（default-deny）** 语义：有 Deny 匹配则拒绝，否则至少有 Allow 匹配则允许。
  - **配置（Configuration）**：由证书、策略集、证书-策略映射、设备集和设备-证书映射构成的五元组。
  - **权限判定**（定义 5）：`P |~ (α, ρ)` 当且仅当存在 Allow 语句匹配资源 ρ 且不存在 Deny 语句匹配 ρ。

- **信息流图（Information Flow Graph）**
  - 定义 I/O 集合（定义 6）：`TIc` 为使用证书 c 的设备可接收消息的主题集合；`TOc` 为可发布消息的主题集合。
  - 信息流图（定义 7）是一个二部有向图 `G = (D ∪ T, E)`：设备 d 到主题 t 的弧（若 d 可发布到 t）、主题 t 到设备 d 的弧（若 d 可订阅并接收 t 的消息）。
  - 设备 d 到 d′ 的**信息流**定义为图中存在从 d 到 d′ 的路径——信息流验证归约为图可达性问题。

- **符号信息流图（Symbolic Information Flow Graph）**
  - 由于主题集合可能无限（AWS 主题最长可达 256 字节），论文引入符号化表示：以逻辑公式代替具体的主题节点。
  - **权限谓词**（定义 8）`ψ(c, id, α, ρ)`：编码策略实例化后权限授予条件（Allow 析取 ∧ ¬Deny 析取）。
  - **I/O 谓词**（定义 9）`Ic(t)` 与 `Oc(t)`：分别编码证书 c 可接收/发布主题 t 的条件。
  - **符号信息流图**（定义 10）：对每对证书 (c, c′)，构建公式 `Fc,c′ = ∃t. Oc(t) ∧ Ic′(t)`；若满足，则添加一个符号节点 `Fc,c′`，并连接设备（证书所属者）与该节点。
  - **关键定理（Theorem 1）**：符号图与原始信息流图在可达性上等价（sound and complete），因此验证可归约为符号图可达性。

- **SMT 求解与启发式算法**
  - 核心挑战：判断公式 `Fc,c′` 的可满足性涉及字符串、正则表达式、两种类型通配符（AWS 与 MQTT）以及 `$clientId` 替换，直接求解代价极高。
  - **Algorithm 2（启发式三阶段求解）**：
    1. **早失败（Early Fail）**：删除 `t ∈ L(tf_mqtt)` 约束，只检查各类权限谓词的可满足性——必要条件；若不满足则直接返回 False。
    2. **早成功（Early Success）**：假设主题 t 与主题过滤器 tf 完全相等（`t = tf`），检查充分条件；若满足则直接返回 True。
    3. **硬策略（Hard Strategy）**：利用 AWS 主题的层次结构（最多 8 层），将匹配约束分解为两种情况——(a) 主题与过滤器层级相同、逐层匹配或使用 `+`；(b) 过滤器以 `#` 结尾匹配剩余层级。通过枚举 n = 1 到 8 的层级组合构造可满足性公式。
  - 该启发式极大提升了实际性能：约 90.4% 的情况走早失败、7.1% 走早成功，仅 2.5% 需要硬策略。

### 6. 主要结论与发现

- 论文提出的信息流图（及其符号化版本）能**准确、完备地刻画**访问控制策略所允许的设备间信息流，且将信息流验证严格归约为图可达性问题（Theorem 1 和 Theorem 3 提供了形式化正确性保证——符号图与操作语义定义的实际信息传播一致）。
- 案例研究证明工具能有效检测**非预期信息流**：例如，由于灯泡策略过度宽松（使用了 `floor?` 和 `$clientId` 通配符），本应仅供首层门禁系统内部使用的锁信息会经由存在传感器流向二层的灯泡——`lock1 → prsSens1 → light2` 路径暴露了机密性漏洞。
- 可扩展性实验表明：对于 258 个规模的真实策略配置，IOT:POKER 构建符号图只需要约 **63 秒**，1000 次查询平均响应时间小于 **0.1 秒**；大规模下构建时间仍处于可用范围。
- cvc5 作为 SMT 后端显著优于 Z3（在构建时间上约为 Z3 的一半或更短，例如 258 证书时 cvc5 平均 62.35s vs. Z3 141.24s）。
- 启发式算法效果显著：绝大多数证书对（约 97.5%）可通过简单检查（早失败/早成功）快速判定，仅少数需要昂贵的硬策略求解。

### 7. 优点

- **选题切中实际安全痛点**：现有云 IoT 访问控制验证只关注单条策略的权限是否正确，未考虑跨设备/跨策略的间接信息流；本文填补了这一空白。
- **形式化基础扎实**：从资源、策略、配置到权限判定均给出严格的形式化定义，并将信息流验证与操作语义（附录 A 中的 MQTT 代理 LTS）建立了精确的一致性证明（Theorem 3）——保证了信息流图不是凭直觉而是语义正确的。
- **符号化处理聪明**：将原始信息流图中的无穷主题节点编码为逻辑公式，借助 SMT 求解器构建图的有限表示，解决了主题空间爆炸的问题。
- **算法设计注重实用性**：三阶段启发式（早失败/早成功/硬策略）充分利用了 AWS 主题结构的特点（最大 8 层深度），使 SMT 求解在大多数情况下极快。
- **工具开源可用**：IOT:POKER 已在 GitHub 上开源，且支持四种安全查询（flow / onlyAffects / onlyKnows / isolated），对实际运维有直接价值。
- **支持扩展性讨论**：论文讨论了如何将模型扩展至 AWS things、Condition 字段等更丰富的策略特性，对未来研究有启发。
- **实验标准明确**：可扩展性实验使用真实世界策略，重复 30 次并报告平均/最差情况，可信度较好。

### 8. 不足与局限

- **模型覆盖范围有限**：
  - 仅覆盖 AWS IoT Core 的**核心**动作（Connect / Publish / Subscribe / Receive），忽略了一些高级 IAM 特性（如资源级条件、临时凭据、ARN 中其他组件的通配符、Amazon Cognito 认证等）。
  - 未显式建模 AWS IoT "things" 与自定义属性（论文说明扩展方向，但工具对 things 的支持要求预定义绑定）。
- **实验真实度受限**：
  - BAS 有效性评估基于**合成配置**，缺少真实多设备 IoT 部署策略的验证（作者在文中也承认了这一点）。
  - 可用性评估虽使用真实策略但设备是随机关联的，且设备数量上限 258，未测试更大规模下的表现。
- **威胁模型假设较强**：
  - 假设云基础设施（代理/认证）被完全信任，攻击者只能控制终端设备——真实世界可能发生云侧攻击或策略篡改。
  - 将设备视为黑盒，完全基于策略允许的行为做**过近似**（over-approximation），不区分设备是否真的会发送/接收特定消息。
- **静态分析的固有限制**：
  - 不包括设备传感器/执行器通过物理环境的**间接信息流**（如温度变化触发开关动作），论文只在未来工作中提到。
  - 不考虑策略随时间动态变化（设备加入/离开、策略更新）——分析是一次性快照。
  - 信息流图中"路径存在"只证明某种信息流**可能**发生，不提供概率或频次信息——存在潜在误报。
- **SMT 求解的理论复杂性**：
  - 最坏情况仍是指数级的（Theorem 2 承认 f 至少指数），对于策略结构复杂（大量通配符与嵌套变量）的配置可能难以扩展；论文的实验策略相对简单，这类极端情形未覆盖。
