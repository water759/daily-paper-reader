## 摘要
大型语言模型（LLM）智能体越来越多地被应用于真实世界的安全运营中，它们能够访问主机工件和命令行界面（CLI），因此彻底评估其安全能力至关重要。然而，现有的网络安全基准测试侧重于入侵前场景，即智能体在攻击发生前被置于一个干净且理想化的环境中。这使得入侵后场景尚未被充分探索。为填补这一空白，我们引入了SecRespond，这是首个针对入侵后应急响应工作流程评估LLM智能体的基准测试。给定一个被入侵主机的取证磁盘快照，以及主机安全产品报告的警报、漏洞扫描和基线检查结果，智能体需要生成入侵取证报告、基线风险和漏洞风险报告，以及补救计划。我们在10个网络靶场中实例化该任务，每个靶场由不同的被入侵云主机构建，涵盖4种入口点类型、21种ATT&CK技术和5种操作系统。我们在OpenCode智能体框架上评估了23个前沿LLM。实验结果表明，尽管当前智能体能够可靠地揭示警报暴露的问题，但它们难以主动调查磁盘中的静默入侵，并生成全面、经过验证的补救计划，没有任何模型能在任何一个靶场上实现完全检测和补救。这揭示了为真实世界应急响应构建智能体的根本瓶颈。该基准测试公开于：https://github.com/Alibaba-NLP/qqr/tree/main/data/secrespond。

## Abstract
Large Language Model (LLM) agents are increasingly adopted in real-world security operations with access to host artifacts and command-line interfaces (CLIs), making it critical to thoroughly assess their security capabilities. However, existing cybersecurity benchmarks focus on pre-compromise settings where agents are placed in a clean and idealized environment before an attack occurs. This leaves the post-compromise setting underexplored. To address this gap, we introduce SecRespond, the first benchmark for evaluating LLM agents on the post-compromise incident-response workflow. Given a forensic disk snapshot of a compromised host together with the alerts, vulnerability scans, and baseline checks reported by a host security product, agents are required to produce forensic reports on intrusions, baseline risks, and vulnerability risks, together with a remediation plan. We instantiate this task across 10 cyber ranges, each constructed from a distinct compromised cloud host, spanning 4 entry-point types, 21 ATT&CK techniques, and 5 operating systems. We evaluate 23 frontier LLMs on the OpenCode agent harness. Experimental results show that although current agents can reliably uncover the problems exposed by alerts, they struggle to proactively investigate the disk for silent intrusions and to produce comprehensive, verified remediation plans, with no model achieving complete detection and remediation on any single range. This reveals a fundamental bottleneck in building agents for real-world incident response. The benchmark is publicly available at https://github.com/Alibaba-NLP/qqr/tree/main/data/secrespond.

## 1. 论文的核心问题与整体含义

**研究动机**：现有网络安全基准（如 Cybench、CyberGym、AutoPatchBench 等）均聚焦于 **攻击前（pre-compromise）** 场景，即智能体在干净理想的环境中执行漏洞发现、利用或修补。然而，真实安全运营中更关键的是 **入侵后（post-compromise）** 场景——主机已被攻陷，智能体需要基于残留的取证痕迹进行主动调查、攻击链重建和系统修复。目前缺少对此类任务的系统性评估。

**核心问题**：当前 LLM agent 能否像专业安全分析师一样，从一个被攻陷主机的磁盘快照中主动发现所有入侵痕迹、理解攻击过程，并生成全面可验证的修复方案？

**整体贡献**：论文提出 **SecRespond**，首个针对入侵后应急响应全流程的基准测试，包含 10 个由真实被攻陷云主机构建的网络靶场，覆盖 4 种入口点、21 种 ATT&CK 技术、5 种操作系统，并设计了分层能力评估框架。通过评估 23 个前沿 LLM，揭示了 agent 在主动调查和完整修复方面的根本瓶颈。

## 2. 论文提出的方法论

**核心思想**：将入侵后应急响应分解为可量化的子任务，要求 agent 基于取证磁盘快照和主机安全产品产生的警报、漏洞扫描、基线检查结果，输出五份报告（进度、入侵、漏洞、基线、修复计划）。通过构造包含真实攻击痕迹的靶场，结合细粒度检查点（checkpoint）和 LLM-as-a-Judge 进行自动评分。

**关键技术细节**：
- **靶场构建**：采用三层设计——蓝图层（定义场景目的与能力需求）、实例层（在真实云主机上执行完整网络攻击）、检查点层（将工件转化为可验证的评分单元）。攻击通过真实网络协议完成，60-70% 的痕迹不会触发警报（静默入侵）。
- **能力分类法（CAP 分类法）**：五维 52 项能力 —— 入侵实体（ENT, 12 项）、持久化机制（PER, 21 项）、基线风险（BAS, 7 项）、漏洞风险（VUL, 4 项）、调查与响应质量（Q, 8 项）。
- **检查点评分**：每个检查点按两个轴评分：
  - **检测轴（Detection）**：满分 3 分，包括发现（1）、证据（1）、归因（1）。
  - **计划轴（Planning）**：满分 2 分，包括正确性（1）、完整性（1）。
- **聚合指标**：
  - CHK-score_a^c = s_a^c / M_a (M_det=3, M_plan=2)
  - CAP-score_a = (1/|C_a^{CAP}|) * Σ CHK-score_a^c
  - Range-level CHK-score_a^r = (1/|C_a^r|) * Σ CHK-score_a^c

**算法/流程说明（文字）**：
1. 蓝图设计 → 攻击脚本开发 → 受害机准备 → 部署 → 验证 → 攻击前快照 → 攻击环境部署 → 执行攻击 → 验证攻击 → 收集安全数据 → 验证修复 → 攻击后快照。
2. agent 接收磁盘路径和三个 JSON 文件（警报、漏洞扫描、基线检查），通过 CLI 工具读取文件，输出五份 Markdown 报告。
3. 三个独立 LLM 裁判（Claude Opus 4.7、Gemini 3.1 Pro、GPT-5.4 Pro）读取报告并根据检查点列表逐项评分，取平均作为最终分。

## 3. 实验设计

- **数据集/场景**：10 个网络靶场，每个靶场是一个完整被入侵的云主机磁盘快照。覆盖 4 种入口点（SSH 弱密码、已知 CVE、业务代码漏洞、供应链攻击），21 种 ATT&CK 技术，5 种操作系统（CentOS 7/8、Ubuntu 20.04/22.04、Windows Server 2019）。每个靶场包含 20-45 个检查点，共 280 个检查点。
- **Benchmark 构成**：每个任务模板要求 agent 生成 `progress.md`、`intrusion-report.md`、`vuln-report.md`、`baseline-report.md`、`remediation-plan.md`。评估基于 280 个检查点的检测和计划得分。
- **对比方法**：
  - 主实验：23 个 LLM（Claude Opus 4.7/4.6/4.5, Claude Sonnet 4.6/4.5, GPT-5.5/5.4 Pro/5.4/5.2 Pro, Gemini 3.1 Pro/3 Flash, GLM-5.1/5, DeepSeek V4 Pro/V3.2, Qwen3.7 Max/Plus/3.6 Plus/3.5 Plus, Kimi K2.6/2.5, MiniMax M2.7/2.5）。所有模型使用同一 agent 框架 OpenCode。
  - 额外对比：传统无代理扫描方法（agentless detection baseline），基于静态模式匹配的扫描器，仅生成发现列表。
  - 消融实验：对 4 个代表性模型（Claude Opus 4.7、GLM-5.1、GPT-5.4、GPT-5.4 Pro）引入人工设计的过程技能（procedural priors），观察性能提升。

## 5. 实验数量与充分性

- **主实验**：23 个 LLM × 10 个靶场 = 230 组独立 agent 运行。每个运行由 3 个 LLM 裁判独立评分（共 230×3=690 次评分过程），覆盖 280 个检查点，产生大量细粒度分数。
- **技能增强实验**：4 个模型 × 10 个靶场 = 40 组，与无技能版本对比。
- **人机一致性验证**：随机选取 60 个检查点，由安全专家对 10 个轨迹评分，与 LLM 裁判对比（Pearson r=0.96，QWK κ=0.94，MAE=0.15）。
- **裁判间一致性**：三个裁判在 72-75% 检查点上完全一致，Spearman ρ=0.86-0.87。
- **充分性评价**：实验覆盖多种模型家族、版本演进、多种攻击复杂度、多种操作系统（包括 Windows），且进行了消融和对比。实验设计公平，所有模型使用相同 agent 框架和任务模板。但在 agent 框架选择上仅使用 OpenCode，未测试其他框架（如 ReAct、AutoGPT 等），因此框架泛化性未验证。

## 6. 论文的主要结论与发现

1. **检测远优于规划**：所有模型在检测轴得分高于规划轴（例如 GPT-5.5 检测 70.7% vs 规划 36.0%），差距最大达 34.7%。模型能发现问题但无法提出完整已验证的修复。
2. **模型性能高度不均**：Claude Opus 4.7 综合最高（检测 79.0%，规划 65.7%），Gemini 系列最低。开源模型（GLM-5.1、DeepSeek V4 Pro）超过 GPT 系列，表明专有模型不保证更强。
3. **版本演进非单调提升**：多数模型系列（Claude Opus、GLM、DeepSeek、Qwen）新版本提升明显，但 Kimi K2.6 规划低于 K2.5，Gemini 3.1 Pro 低于 Gemini 3 Flash。
4. **攻击链越长代理越弱**：线性攻击（如 Log4j-RCE、Docker-Escape）得分高；多步跨服务、跨运行时、伪装持久化的场景（如 NPM-Worm、ASP.NET-ViewState）得分低。
5. **能力维度严重失衡**：检测方面，入侵实体平均 75.4%，持久化机制仅 58.8%；规划方面，基线风险 55.3%，调查与响应质量仅 31.8%。模型擅长显式痕迹，对隐式持久化（如 bashrc、profile.d、DLL 劫持）几乎无效。
6. **传统扫描远弱于 agent**：无代理扫描器在持久化检测上仅 2.1%，而 agent 平均超过 50%，且能构建攻击链和生成修复。
7. **过程技能可提升但无法消除瓶颈**：提供手工过程技能后，弱模型规划得分提升 40-50%，但强模型可能因技能边界而降低探索意愿（如 GLM-5.1 在 Shiro-Fastjson 检测下降 12%）。

## 7. 优点

- **填补空白**：首个专注入侵后事件响应的基准，弥补现有攻击前基准的不足。
- **真实性强**：靶场基于真实云主机、真实网络攻击、真实工件构造，而非合成日志。
- **细粒度评估**：280 个检查点映射到 52 项能力，支持在单个维度诊断模型强弱。
- **多裁判机制**：三个独立 LLM 裁判评分，减少单一模型偏好；验证了与人类专家高一致性。
- **公开可复现**：代码和数据开源，包含完整构建流水线和检查点列表。
- **广泛的模型覆盖**：23 个模型，8 个系列，包含多版本演进分析，结论具有普遍性。
- **识别关键瓶颈**：明确指出 agent 在主动系统级调查和完整修复验证上的根本不足。

## 8. 不足与局限

- **环境合成性**：虽然攻击是真实的，但靶场环境仍是实验室构造，缺乏真实生产环境中的多租户干扰、数据污染、合规约束等因素。
- **agent 框架单一**：仅使用 OpenCode，未探索其他框架（如 ReAct、Planning 式、多代理协作）的影响，结论可能对框架选择敏感。
- **LLM 裁判偏差**：尽管采用多裁判平均，但裁判本身是 LLM，可能对自身模型家族或结构化报告有偏好（论文实验显示此偏差较小但存在）。
- **Windows 靶场覆盖有限**：仅 2 个 Windows 靶场，且 Windows 原生取证工具（如 PowerShell、注册表）需在 Linux 上通过 `strings` 等操作，可能增加 agent 负担。
- **技能增强实验的设计**：手工技能仅包含过程程序，未涉及领域知识；且技能设计来自作者团队经验，不一定最优，导致部分模型性能下降。
- **代理无法联网进行验证**：修复计划中要求验证（如重启后服务正常），但 agent 仅生成文本计划，无法实际执行，因此规划轴的“完整性”评分依赖于计划文本，而非执行结果。
- **缺乏实时交互**：任务基于静态快照，agent 无法与活跃系统交互（如查看实时进程、网络连接），这限制了动态发现的模拟。
