## 摘要
大语言模型代理日益依赖外部工具，这扩展了能力的同时也创造了新的安全边界：第三方工具可能在接口层面看似良性，但在实现中嵌入不安全行为。现有防御措施依赖弱元数据，将特征描述与策略判断合并为单一决策，或使用基于启发式/大语言模型的执行方式，缺乏对任务上下文和多工具组合的确定性、可审计推理。本文提出ToolGuardian，一个策略驱动框架，通过预准入审查和任务感知的运行时授权来保护代理-工具交互。ToolGuardian使用渐进式特征描述将证据转化为结构化事实：描述捕获声明意图，系统调用轨迹暴露粗略行为，模拟执行揭示观察到的效果，源代码分析识别潜在行为。ToolGuardian的核心贡献是基于回答集编程（ASP）的声明式策略层，该层明确推理能力、效果、任务上下文和组合。我们使用相同的输入和输出合约，将ASP与基于启发式和大语言模型的策略实现进行比较。我们在16个MCP风格工具（包括8个源自真实开源工具的恶意变体）以及20个运行时场景上评估ToolGuardian。在审查阶段，使用描述、系统调用和观察到的效果证据，ASP的拒绝类F1得分为0.86，准确率为88%。在运行时授权方面，完全指定的实现正确分类所有场景，而消融实验表明，移除组合性和合规性规则会显著降低性能。

## Abstract
LLM agents increasingly rely on external tools, expanding capability while creating a new security boundary: third-party tools may appear benign at the interface level while embedding unsafe behavior in implementation. Existing defenses rely on weak metadata, collapse characterization and policy judgment into a single decision, or use heuristic/LLM enforcement that lacks deterministic, auditable reasoning over task context and multi-tool composition.   This paper presents ToolGuardian, a policy-driven framework for securing agent-tool interactions through pre-admission vetting and task-aware runtime authorization. ToolGuardian uses progressive characterization to convert evidence into structured facts: descriptions capture declared intent, system-call traces expose coarse behavior, mock execution reveals observed effects, and source analysis identifies latent behavior. ToolGuardian's core contribution is an Answer Set Programming (ASP)-based declarative policy layer that reasons explicitly over capabilities, effects, task context, and composition. We compare ASP against heuristic and LLM-based policy realizations using identical inputs and output contracts.   We evaluate ToolGuardian on 16 MCP-style tools, including 8 malicious variants derived from real open-source tools, and 20 runtime scenarios. For vetting, ASP reaches a deny-class F1 of 0.86 and 88% accuracy using description, syscall, and observed-effect evidence. For runtime authorization, fully specified realizations classify all scenarios correctly, while ablations show that removing compositional and conformance rules substantially degrades performance.

- **整体含义**：提出 ToolGuardian，一个**策略驱动的安全框架**，通过分离工具特征提取（表征）与策略执行，并引入基于 **Answer Set Programming (ASP)** 的声明式策略层，实现**预准入审查**和**任务感知的运行时授权**，以可审计、确定性的方式应对工具交互中的安全威胁。

## 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：将安全决策建立在**结构化事实**（structured facts）之上，这些事实从渐进式表征过程获得，然后由独立的策略层进行逻辑推理。
- **关键技术细节**：
  - **渐进式表征（Progressive Characterization）**：四个累积层级：
    - **P0**：基于工具描述（声明意图）——最便宜但不可信。
    - **P1**：P0 + 系统调用轨迹（粗粒度操作行为）。
    - **P2**：P1 + 模拟执行（观察到的实际效果，如网络请求、数据访问）。
    - **P3**：P2 + 静态源码分析（AST 分析，发现潜在或条件性行为）。
  - **事实表示**：统一事实词汇（如 `capability(T, network_access)`, `effect_mismatch(T, undeclared_network_access)`），适用于审查和运行时。
  - **ASP 声明式策略层**：使用 Clingo 求解器，编码拒绝条件、例外、效果合规性、组合约束等规则。例如：
    ```
    deny(Tool) :- capability(Tool, shell_exec), network_access(Tool).
    ```
  - **两个强制阶段**：
    - **工具审查（vetting）**：独立于任务，决定是否准入（拒绝/限制/警告/准入）。
    - **运行时授权（runtime authorization）**：结合任务上下文和调用历史，允许或阻止具体调用，包括原子调用和组合工作流。
- **流程说明**：工具 → 表征（逐步增加证据层） → 生成结构化事实 → 策略层（ASP/启发式/LLM）推理 → 输出决策（allow/deny/restricted）及解释标签。

## 6. 论文的主要结论与发现

- **审查阶段**：ASP 在 P2 表征下达到最佳性能（deny 类 F1=0.86，准确率 88%）。P3 增加静态分析会暴露良性工具的高风险能力（如进程执行+网络），导致过阻塞，F1 略降至 0.82。
- **运行时阶段**：完全指定的策略（ASP、启发式、LLM）**全部正确分类 20 个场景**（包括所有组合 deny 案例）。
- **消融关键发现**：
  - 移除 LLM 显式组合规则、效果合规性等指导，准确率从 100% 降至 75%，F1 降至 0.84。
  - 移除启发式组合推理后，组合 deny 场景全部漏报；移除更多规则后原子场景也出现错误。
  - 结论：**结构化事实本身不足以保证安全，显式的组合和合规性规则至关重要**。
- **表征深度**：从 P0 到 P2 改善检测，但 P3 带来新的安全-效用权衡——更多可见性可能导致良性工具被过度限制。
- **策略实现比较**：ASP 提供确定性、可审计且支持复杂组合规则；启发式在 P2 与 ASP 持平但 P3 过严格；LLM 在有结构指引时表现良好，但依赖提示且成本较高。

## 7. 优点：方法或实验设计上的亮点

- **架构创新**：将**特征提取与策略执行分离**，使得不同策略实现可以在相同证据上比较，也支持渐进式证据积累。
- **声明式策略（ASP）**：自然表达多条件组合、例外和传播规则；决策过程确定、可审计、可解释（规则可生成解释标签）。
- **两阶段强制**：区分预准入审查和运行时授权，解决了“同一工具在不同任务中安全风险不同”的问题。
- **组合安全性**：显式建模 source-sink 数据流和顺序依赖，是处理多工具工作流风险的核心贡献。
- **实验设计亮点**：使用相同的输入事实和输出合约比较三种政策实现，并进行多层级表征消融和运行时消融，逻辑严谨。

## 8. 不足与局限

- **基准规模与多样性**：仅 16 个工具（8 良性 +8 恶意），20 个运行时场景，**远未覆盖真实 MCP 生态的多样性**，且恶意变种为人工构造，可能偏离实际威胁分布。
- **MCP 特定性**：框架和实现围绕 MCP 风格工具设计，对浏览器代理、代码执行代理等其他代理-工具接口的泛化性未经验证。
- **组合深度有限**：组合场景仅包含短工作流（2-3 步），未考虑更长链条、间接依赖、时间约束等复杂情况。
- **ASP 规则设计成本**：政策规范需要专家手动编写，定义了涉及能力、效果、组合的规则词汇，**缺乏自动化生成或验证方法**，且未证明规则完备性。
